01 · The starting question

Where does LoRA go?

Nowhere in app/. The backend is a thin HTTP client to LM Studio — five dependencies, no ML libraries, no model weights. Fine-tuning doesn’t slot into it because there’s nothing there for it to slot into.

LoRA is a separate offline subsystem beside app/ and eval/, and its only runtime touchpoint is one config value naming which model LM Studio serves. That shape matters: a fine-tune can be swapped in or rolled back without touching application code.

The dependency arrow only ever points one way:

training/  ──imports──▶  eval/  ──imports──▶  app/
   ▲                                            │
   └────────────── never ───────────────────────┘

training/ must import from app/ — that’s the whole point. A training example has to be built by the same code that builds an inference prompt, or the model learns a format it never sees in production. What must never happen is app/ importing either.

The real work was never the training script. It’s being able to tell whether the training script helped — and that has to exist first, or the answer is unfalsifiable.

02 · The plan

Three stages, two hard gates

Eval infrastructure → dataset → training. The order is the whole design.

Three objectives were chosen for the fine-tune: (a) format and citation discipline, (b) refusal calibration, (c) Arabic register. Explicitly not knowledge injection — RAG owns that, and a 20,000-character corpus can’t teach facts to weights without inviting hallucination.

Gate 1 · before anything else

Measure the baseline

The base model may already do what the fine-tune was meant to teach. If so, the work is pointless, and the cheapest possible way to discover that is an hour of inference — versus roughly ten hours of human dataset review spent teaching a model something it already does.

This gate fired. See section 05.

Gate 2 · before any dataset work

Prove the model survives the round trip

google/gemma-4-e4b is almost certainly a Gemma-3n MatFormer — per-layer embeddings, a nested submodel, non-standard module names like altup and laurel. Its adapter → merge → GGUF path isn’t well-trodden and fails late.

The spike: rank-4 adapter, five lines of garbage data, ten steps, merge, convert, load back into LM Studio. Quality irrelevant — the only question is whether the pipeline completes. If it doesn’t, switch to Qwen 3, which is cheap because A1 made the model a card rather than a constant. Not yet run.

03 · Stage A

What got built

Ten increments, each independently checkable. That’s why they’re split.

A0

Commit the work in progress

Prompt versioning, the eval harness, and the testing page were all untracked. Committed first so everything after had a rollback point.

A1

A model registry — app/model_registry.py, app/models/*.md

Model identity becomes data in a file. A card names the exact string LM Studio serves, plus the provenance a fine-tune needs: base model, training run, dataset hash, and the prompt version it was trained against.

That last field is load-bearing. A LoRA learns the wording it saw; pair it with a different prompt version later and it quietly underperforms for a reason nobody remembers six weeks on.

Deviation from plan: the plan said import _split_frontmatter from prompt_registry. Instead it was extracted to app/frontmatter.py — reaching into another module’s privates would have coupled the two registries for no conceptual reason.

A2

GET /models

A direct mirror of the existing GET /prompts, so the testing page can pair the two dropdowns into a (prompt × model) picker.

A3

Plumb the model choice through the API

stream_completion couldn’t carry a model override at all — only the non-streaming path could, and the UI uses streaming. So the streaming path physically could not honour a model choice.

Also fixed a drift bug: the stream’s done event reported the model read from the prompt frontmatter, which only records what the wording was tuned against. It now reports the identifier that actually went out on the wire.

A4

Score variants, not prompt versions

The unit an eval scores is now a Variant — v2@base, pairing a prompt version with a model. Scoring the combination is also how the coupling between them gets measured rather than assumed.

Two operational details: models iterate in the outer loop, because LM Studio JIT-loads a model on first use and the alternative thrashes; and --models defaults to just the active model, because the full cartesian product is hundreds of local generations and should be opt-in.

A5

Save what actually happened — eval/records.py

Runs printed a scorecard and discarded everything else. Now each case writes a JSON line: question, expected outcome, the exact sources block the model saw, the full answer, per-scorer results, resolved model, sampling params, timing.

Rates say a case failed; only the text says why. Three of the seven bugs below were found by reading these records, and two of them were bugs in the scorers themselves.

A6

Separate declining from refusing

The most consequential change of the session — full detail in section 04.

A7

5 cases → 59, every label measured

With three answerable cases, one flip moved a rate by 33 points. Every candidate was probed against real retrieval before being written down; four were relabelled or dropped because their behaviour contradicted the intent.

Each case records its measured top score in a comment, so the labels stay checkable when the corpus or threshold changes.

A8

An independent judge — ClaudeJudge

The comparison ahead is “base model vs. a LoRA of that base model.” A local Gemma scoring both sides is a model grading two variants of itself — it can’t penalise a fabrication it would also have made.

Lazily imported, in requirements-data.txt rather than requirements.txt, so the five runtime dependencies stay five and the local judge keeps working with none of it installed.

A9

The baseline run complete

59 cases × 2 prompt versions = 118 generations at ~31 seconds each. Records committed as eval/results/baseline-20260728-094100.jsonl (644 KB).

04 · A6 in detail

One boolean was hiding the thing worth measuring

Every eval case carried should_refuse: true|false. It collapsed two events that have nothing to do with each other.

Three outcomes, not two
OutcomeWhat happensWhose behaviour
refused Retrieval scores below threshold. The app returns a canned string — no model ever runs. code
declined Sources come back above threshold but don’t contain the answer. The model says so. model
answered The model answers from the sources. model

The highlighted row is the hard one, and it was invisible. A question whose sources scraped past the threshold without covering it was labelled should_refuse: false, so has_citation and ruling_line_present penalised a model for correctly saying “these don’t answer this” — and rewarded one that answered anyway.

Objective (b) was unmeasurable by construction. Any work aimed at calibration would have registered as a regression.

The replacement is deliberately symmetric

decline_correct fails a model that answers from weak sources and one that declines when the sources were fine. A one-sided “did it decline?” check would be trivially satisfied by a model that declines everything — which would look like a fine-tuning win while being a serious regression.

Gotcha worth keeping

Arabic diacritics silently break substring matching

Detecting a decline means matching phrases like لا تتضمّن. Models emit tashkeel inconsistently — the same word arrives as تتضمّن or تتضمن depending on the sample. Raw matching would have missed half the output and produced a plausible, wrong number. Both sides are normalised (diacritics and tatweel stripped, alef forms unified) before comparison.

Gate 1 · fired

Objective (a) is already at ceiling

On v2 the stock model emits the labelled ruling line on 41 of 41 answered cases, cites at least one source on 41 of 41, and never once cites a source number that doesn’t exist — 59 of 59 across every case.

Format and citation discipline was one of the three things the LoRA was going to teach. There is nothing left to teach.

And ruling_line_present scoring 1/41 on v1 proves this is a real measurement rather than a scorer that passes everything — the prompt change alone moved it from 1 to 41. The instrument works; the objective is just already met.

The model does not fabricate

Across all 118 generations, no invented figures were found. Where the model fails it evades — answers a nearby question, or quotes the source’s own vague phrasing back as though it were the answer. That is a different and far less dangerous failure than making up a number, and it was the specific risk the declined-case design was built to catch.

Two answers worth reading in full

A correct decline, on a case where the corpus covers the topic but omits the figure:

ومع ذلك، فإن المصادر القانونية المقدمة لا تتضمن تفصيلاً محدداً لـ:

That is close to ideal: it establishes what the sources do say, names precisely what is missing, and declines. It is also why one of the scorers turned out to be wrong — see bug 5.

06 · Findings

Seven bugs, and who owns each

Three in the product, three in the measurement, one in the process.

1 · The relevance threshold is miscalibrated product

Questions the corpus demonstrably answers fall below the 0.5 gate.

False refusals
QuestionScoreWhere the answer is
ما المعيار الحاكم في إسناد الحضانة؟0.491 family §4 — the section is custody
من هو الحامل حسن النية؟0.444 negotiable §3 — states it verbatim
ما حكم تعسف المالك في استعمال حقه؟0.497 property §4 — states the rule verbatim
Bankruptcy priority — genuinely absent from the corpus0.484 — scores above two of the answerable ones

The populations overlap, so no single threshold separates them. 0.5 was a guess and is the one number in the pipeline never checked against data. Deliberately left alone — changing it would move the yardstick out from under the baseline. Documented in the README.

2 · A real case gets refused product

Pasting a full plaintiff-vs-defendant case into the Ask page returns “not enough information.” A 250-word case embeds to an average of many topics and matches no single 500-character chunk strongly. The system can’t accept the input format its own prompt was written for — the prompt says “propose the ruling based on the case presented.” Not yet measured precisely.

3 · The spinner never clears on a refusal product

In ask.ts, the token branch calls stage.set(null); the refused branch doesn’t. So the answer renders while جارٍ البحث في الوثائق… stays on screen forever. One line.

4 · A case label was wrong — mine, not the model’s measurement

tort-negligence-vs-intent flagged as an over-decline. Reading the record: the model analysed negligence correctly from tort_principles, then observed the sources contain no definition of intent — and it was right. Retrieval returned only negligence chunks; intentional_torts_overview never came back. The question needs two documents and got one. It tests retrieval recall, not the model.

5 · A scorer encodes a wrong opinion measurement

no_citation_when_declining scored 0/12 — alarming, until you read what the model does. It cites [1] to establish what the sources do say, then names what is missing. That is better than a bare decline, and the scorer marks it failed. The assertion “a decline cites nothing” was mine, and it was wrong.

6 · The decline detector has a gap measurement

declined-protest-procedure counted as an under-decline, but its answer says لا تحدد أو تصف تفاصيل هذه الإجراءات — a decline phrased with لا تحدد, which isn’t in DECLINE_MARKERS. Some of the remaining decline_correct failures are the detector, not the model, so the true calibration gap is smaller than 48/53 suggests.

7 · Mangled commit messages process

The first commit used PowerShell here-string syntax (@'…'@) inside the Bash tool, where it doesn’t exist. Bash read it as a literal @ plus a quoted string, so the commit shipped with a subject line of @ Add prompt versioning…. Caught when the same syntax broke outright on an apostrophe. Amended before pushing; all later commits use heredocs.

07 · The decision

What’s left of the case for fine-tuning

ObjectiveBaselineVerdict
(a) Format + citation discipline 41/41 · 41/41 · 59/59 dead nothing left to teach
(b) Refusal calibration 48/53 (~91%) shrunk and partly measurement bugs
(c) Arabic register — unmeasured guardrails can’t see it

Honestly: the value proposition got much weaker in the space of one hour. Objective (a) is gone outright. Objective (b) sits around 91% and at least some of the failures are bugs 4–6 above rather than model behaviour — the real gap may be two or three cases out of 59, which is close to the noise floor at this sample size.

That leaves (c), which is the hardest of the three to measure, the least certain to improve, and currently has no number at all.

This is not a disappointing result. It is the result the staging was designed to produce, arriving at the cheapest possible moment — before the dataset, before the GPU, before ten hours of review.

The cheap next move is to fix bugs 4–6 and re-score from the saved records with zero inference — which is possible only because A5 stored the full answers — then run the rubric judge for a first read on (c). About an hour, and it settles whether Stage B is worth starting.

09 · Reference

How to run any of it

All from backend/, with LM Studio and Qdrant up.

# Guardrails only, active model, all prompt versions
python -m eval.run_eval --no-judge

# Compare specific prompt versions and models
python -m eval.run_eval --prompts v1 v2 --models base lora_v1

# Name the output file (results land in eval/results/)
python -m eval.run_eval --no-judge --label baseline

# With an LLM judge for the 1-5 rubric
python -m eval.run_eval --judge local     # local Gemma; self-biased
python -m eval.run_eval --judge claude    # independent; needs the anthropic SDK

# Don't write a results file at all
python -m eval.run_eval --no-save

Reading a saved run back, without re-running any inference:

from pathlib import Path
from eval.records import load_records

recs = load_records(Path('eval/results/baseline-20260728-094100.jsonl'))
by = {(r.variant, r.case_id): r for r in recs}
print(by[('v2@base', 'declined-patent-term')].answer)

The Claude judge needs one extra install, deliberately kept out of the runtime set:

pip install -r requirements-data.txt
# then either:
export ANTHROPIC_API_KEY=...
# or:
ant auth login

10 · Open

Unresolved

  1. Does the LoRA still have a case? The live question. Objective (a) is dead; (b) is small and partly noise; (c) is unmeasured.
  2. Your VRAM is still unknown. Every hyperparameter in Stage C is conditional on it, and it’s step one of the Gate 2 spike.
  3. Gate 2 hasn’t run. Whether gemma-4-e4b can complete adapter → merge → GGUF → LM Studio at all is unknown.
  4. Bugs 1–3 are unfixed — threshold, long-case dilution, spinner. All three are product bugs independent of the fine-tuning work, and arguably better value than the LoRA right now.
  5. The eval tests questions, not cases. All 59 are definitional; the prompt is written to adjudicate a plaintiff-vs-defendant dispute. Bug 2 means the app can’t currently accept that shape at all.
Stage A’s job was to make “did this work?” boring and checkable — a number beside another number, same questions, same seed. That now exists, and its first act was to argue against the project that built it.
