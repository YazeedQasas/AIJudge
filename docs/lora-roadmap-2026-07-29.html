01 · Where we were

Before this thread: a prompt, and a five-case guess

Prompt versioning (v1 → v2) had just shipped. The eval harness scored exactly one axis — prompt version — over 5 hand-written cases, three of them answerable. Results were printed to a terminal and discarded; nothing was persisted, nothing was judged independently of the model being judged.

The plan going in named three LoRA objectives, all assumed still open: (a) format and citation discipline, (b) refusal calibration under weak retrieval, (c) Arabic register. There was no way yet to tell which of the three the base model already handled — that gap is exactly what Stage A exists to close.

03 · Where we are — Spike 0

The round trip, proven on garbage data

Before any real dataset work: prove HF weights can become a GGUF LM Studio will load, on 5 lines of throwaway data. Full pipeline run, in order: 

HF safetensors → 4-bit (bitsandbytes nf4) load → rank-4 LoRA
  (target_modules: q/k/v/o_proj, gate/up/down_proj — real names, not "all-linear")
→ 10-step train → merge on CPU in fp16
→ convert_hf_to_gguf.py (llama.cpp b10174) → llama-quantize to Q4_K_M
→ llama-server → /v1/chat/completions → coherent, correct answer

Peak VRAM during training: 4.52 GB, on a measured 6 GB card.

Student switched mid-spike

google/gemma-4-e4b turned out to be 8B raw params, BF16-only, and multimodal (...ForConditionalGeneration) — a Gemma-3n MatFormer with per-layer embeddings, not the plain 4B text model its name implies. Exactly the risk Spike 0 was designed to catch, and a bad fit for 6 GB VRAM.

Switched to Qwen/Qwen3-4B-Instruct-2507 — plain dense Qwen3ForCausalLM, ungated, ~8 GB in bf16, first-class PEFT + llama.cpp support. Gemma stays what the live app serves; Qwen is the fine-tuning student.

Two real gotchas, worth carrying into Stage C: the GTX 1660 Ti (Turing, no native bf16) needs plain fp32 adapter training, not fp16=True/GradScaler (NotImplementedError, not a precision tradeoff) — trivial cost at 8M trainable params. And with no local C/C++ toolchain, llama.cpp came from prebuilt Windows CUDA binaries, not a source build.

04 · Where we are — the re-scope

One of three objectives had nothing left to fix

The A9 baseline scored objective (a) — format and citation discipline — at ceiling already: 41/41 on both scorers, on prompt v2 alone. Prompting had already solved it.

A second look at the “declines without citing sources” gap (no_citation_when_declining 0/12) found the same thing: those 12 records already cite what's supported, name the gap, then stop — a coherent structure, not a defect. The eval was scoring a zero-citation rule against partial-coverage answers; a labeling gap in the eval, not a model gap. Still open, independent of which LoRA objective ships.

Decision

Proceed with the LoRA anyway, explicitly as a learning exercise — PEFT/TRL mechanics, quantization, distillation, evaluation design — not a product fix. The measured gap on the current objective is ~0, and that's known going in, not discovered at the end.

The dataset pipeline is wired; the dataset itself isn't built yet

Six of eleven increments done and proven; two more — B7 and B8 — got written since this doc's first pass today, but neither has been run to completion yet. data/v1/drafts.jsonl still holds exactly the one answered example from the original wiring smoke test.

B6

contamination.py + gate.py — hard-errors on an exact match against eval/cases.yaml, warns on high trigram overlap; auto-gate reuses eval/scorers.py wholesale so training data can't ship with an invalid citation.

B7

Negative constructions — build_dataset.py --construction {declined,mismatched,partial} now builds all three: declined reads 13 hand-written declined_seeds.yaml questions that clear the relevance gate but ask for a figure their document conspicuously omits (verified live against Qdrant when written); mismatched forces retrieval onto a deliberately wrong document via search(..., source=); partial mixes 2 genuinely on-topic chunks with off-topic filler from an unrelated doc, so the target cites only what's relevant and still closes with a ruling line. Code complete; not yet run — no construction has produced an example in drafts.jsonl yet.

Written and import-clean; not yet run to completion — no expanded_questions.yaml exists yet, so the 95 seeds haven't grown toward ~380.

wired

06 · Where we're going — Stage C

Training and serving, once B7–B11 land

The second virtualenv (.venv-train, torch/transformers/peft/trl/bitsandbytes) already exists and already trained Spike 0 — that groundwork carries forward. Everything else in Stage C is untouched.

Whether Stage C actually gets built is TBD. This LoRA track is a learning exercise, not a product fix (see the re-scope above — the measured gap on the current objective is ~0). C1–C10 stay planned below as the path if it continues, but there's no commitment yet to carry it through training and serving.

C2

token_stats.py — tokenize every prompt+answer, print p50/p90/p95/max. Sets max_seq_length from the real data, not a guess — each example carries ~2,500 chars of Arabic retrieval context before the question even starts.

planned
C3

check_template.py — render one record through the exact chat template LM Studio applies at inference; a mismatch here degrades silently, not with a crash.

planned

07 · What actually decides the next move

Two gates already passed, one still ahead

A9 said the yardstick was ready. Spike 0 said the round trip works, on this GPU, with this student. Neither says the LoRA is worth finishing — that's C8: the pilot scorecard on 120 records, before spending the other ten hours of review on B12/C10.

Next concrete step is running what B7 and B8 already wired: draft a handful of examples through each of the three negative constructions and confirm they actually reach drafts.jsonl instead of auto_rejected, then run expand_seeds.py for real and skim the output for paraphrases that drifted in meaning without tripping the retrieval check. Only after that is B9's full draft run worth kicking off.

08 · Revision note

What changed since this doc's first pass, same day

Rescanned the repo and updated this page in place. Since the first version: build_dataset.py grew from one construction to four (--construction answered|declined|mismatched|partial), declined_seeds.yaml (13 questions) landed for construction #2, and expand_seeds.py was written for B8. None of the three has been executed to completion yet, so B7 and B8 moved from not started to wired — a distinct state from done, which stays reserved for “ran, and its output exists on disk.”

Also since the first pass: app/retrieval.py was extracted from api/ask.py, adding multi-segment search for long narrative questions (a 1,200-character case narrative embeds as one diluted vector otherwise). Every fixed-length eval case and seed question is short enough to take the unchanged single-query path, so this doesn't move Stage A's baseline or Stage B's drafts — it's noted here only because build_dataset.py and run_eval.py now both import retrieve_chunks from this shared module instead of calling embed_texts + search directly.
